# Warcraft III 可选视频播放：MIX 分发与 LAN 测试经验

整理日期：2026-10-09。实现与验证基于 Windows、经典 Warcraft III 1.27a 和本机 KKWE。本文记录工程方案、踩坑与证据边界，不代表其他版本或平台已兼容。

## 1. 从地图逐帧播放转向可选客户端播放器

逐帧贴图方案需要大量导入文件，视频长度、分辨率和帧率都会增加包体与资源管理负担。本次采用压缩 MP4 + 外置 WPF 播放器：地图发送表现请求，播放器在游戏窗口上覆盖画面，同时播放视频内音轨。

这个方向适合允许玩家安装一个可选文件的项目。地图逻辑必须在缺少插件、素材或解码失败时继续运行。这里采用单向表现请求，不把本地播放完成、视频时长或错误反馈用于地图结算，避免插件安装情况影响同步游戏状态。

真正“有人安装、有人未安装”的联机环境尚未实测；上述是实现约束，不能直接当作混装验证结果。

## 2. 用一个 MIX 同时携带启动器、播放器与 MP4

经典客户端能够加载游戏根目录的 Miles MIX 提供者。本次包前部是可加载的 32 位原生 DLL，后部追加播放器 EXE、MP4、索引及固定尾部，玩家只需要放置一个 MIX。

包布局：

```text
[原生 x86 DLL][播放器 EXE][MP4 数据...][索引][56 字节尾部]
```

尾部包含：
- 8 字节魔数 WVMIX001；
- EXE 偏移、EXE 长度、索引偏移、索引长度，分别为 64 位整数；
- 16 字节包 ID。

启动器读取尾部、校验数据范围并解包播放器；播放器按需提取 MP4。首次播放会写缓存，所以“只分发一个文件”不等于运行时不创建其他文件。删除缓存目录后，完整 MIX 仍应能重建缓存。

每次保存或刷新生成新包 ID，使更新后的素材与旧缓存分开。多个游戏进程共用包时，使用独立临时文件和原子完成；如果另一个进程已经完成有效缓存，可以接受该结果，避免两个客户端争抢同一临时文件而启动失败。

管理器只做导入、导出、删除和保存，不自动转码。原生 DLL 与已封装 MIX 必须明确区分：不能把完整视频包当 DLL 模板再次封装，也不能让原生编译步骤把已封装 MIX 覆盖成裸 DLL。

构建顺序为播放器 → 原生 DLL → 内嵌二者的管理器 → MIX。升级用户已有包采用刷新操作，保留当前包中的 MP4，不能从旧素材清单重建后覆盖用户新导入的视频。

## 3. GUI 精简到六个动作

| 动作 | 接口 |
| --- | --- |
| 播放给所有玩家 | KKWEVideoPlayAll(string) |
| 播放给指定玩家 | KKWEVideoPlayForPlayer(player, string) |
| 停止指定玩家 | KKWEVideoStopForPlayer(player) |
| 停止所有玩家 | KKWEVideoStopAll() |
| 设置音量 | KKWEVideoSetVolume(real) |
| 设置速率 | KKWEVideoSetRate(real) |

地图填写包内文件名；视频时长由播放器读取，音轨随视频播放，无需地图另导入背景音乐。当前音量范围为 0–100%，速率为 0.25–4 倍；这不是音轨增益放大接口。建议 H.264 / YUV420P + AAC 的 MP4，但不保证所有 MP4 都能由系统媒体栈解码。

JASS 库在同步流程中更新经典 12 槽位的文件名、序号和活动状态，仅在 GetLocalPlayer() 分支内写出本地表现请求。不要把调用整个播放动作放进各客户端不同的条件分支，因为动作本身也会更新地图状态。

自动读取视频时长只供播放器表现使用。剧情时间、奖励与关卡推进由地图独立安排，不能依赖本地解码或播放完成。

## 4. 双开必须按游戏进程隔离

最初只有一个窗口播放，问题不只在窗口查找：播放器单实例锁、请求文件、日志和窗口绑定都必须区分游戏进程。

本次实现：

```text
游戏 PID
  ├─ 独立播放器实例 / mutex
  ├─ request-<PID>.pld
  ├─ player-<PID>.log
  └─ 只绑定该 PID 的游戏窗口
```

GUI 写入固定路径 War3Video/request.pld。原生插件通过游戏进程内 IAT 路由，将精确匹配的文件名改为本进程请求文件。不改磁盘 Game.dll、游戏指令、其他文件或同步状态，也不新增 JASS native。

曾发生启动崩溃：改写内核模块导入表可能使原始函数导出转发再次进入钩子，导致递归。修复时排除了 kernel32、kernelbase、ntdll 和插件自身。修改 IAT 仍然需要目标环境验证；这一经验不意味着可以任意扫描、改写其他插件的导入表。

各播放器使用普通窗口层级，跟随各自可见游戏窗口；不能用“只显示前台游戏”作为窗口选择规则。最小化时隐藏画面，本实现音频继续。

## 5. 音频生命周期必须跟随游戏

测试时若只按编辑器或父进程生命周期退出，关闭游戏后编辑器仍存活，视频音频就可能继续播放。

本次播放器定时检查绑定游戏进程是否退出，以及 HWND 是否仍属于绑定 PID。游戏退出或窗口销毁时立即停止媒体并解除绑定。由游戏自动启动的播放器随游戏结束退出；编辑器启动的待命实例可以等待下一局。

同一会话、同一序号的 PLAY 请求也可能只是音量或速率更新。不能用两秒超时推断地图重开，也不能每次收到心跳就从头播放；新地图用新会话标识区分。

## 6. MIX 也会被编辑器加载

KKWE 日志明确显示：编辑器会加载游戏根目录的 War3Video.mix。旧启动器未检查宿主 EXE，因而可能在编辑器内安装文件钩子、提取播放器并启动子进程。

已修复为 DllMain 首先检查宿主名，仅 war3.exe 或 Warcraft III.exe 启用；其他进程直接跳过，不创建工作线程、不安装钩子、不提取缓存、不启动播放器。工作线程用于把后续启动工作移出加载锁，但工作线程本身不能替代宿主过滤。

磁盘文件更新不会撤销旧编辑器实例已加载的钩子；需要重启编辑器后才会使用新版本。应保留未保存工作，不为释放 DLL 占用而擅自关闭用户编辑器。

保存卡住与这次发现同时出现，但现有日志没有证明完整因果链。已确认并修复的是插件错误介入编辑器；用户地图保存问题是否完全消失仍需重启后的复测，不能写成已彻底修复。

## 7. 自动行为测试优先 LAN

单人直接加载地图时，失去焦点可能暂停或影响推进。自动行为测试优先创建 LAN 局，让游戏可以后台运行；画面与真实输入用短时前台检查补充。后台运行不等于锁屏启动已经验证。

同机双开需要真实的两个真人 W3I 槽位。只在脚本中 SetPlayers 不会自动让 LAN 主机生成两个可加入位置。

本次双客户端进入同一 LAN 局，并取得：
- host 日志中两个玩家开始加载；
- 两个独立 War3 进程和播放器；
- 两端解码日志与非零进程音频峰值；
- 同一同步会话的播放、停止和重播记录；
- 停止玩家 0 后玩家 1 继续，重播玩家 0 不重启玩家 1；
- 停止玩家 1 后玩家 0 继续，停止全部结束剩余播放。

声音“正在输出”不能仅凭 PLAY 日志判断，要结合媒体解码和对应进程的音频输出。也不能把采样区间末尾仍有峰值的记录当作最终静音证明；本次停止行为由对应时序和播放器退出日志共同说明。

启动菜单自动化曾受焦点权限影响。使用临时进程内辅助驱动完成所属客户端的菜单动作，驱动必须有本轮 PID 授权、有效期和目标窗口检查，且不能进入生产 MIX。它只服务此次测试，不能包装成无需交互桌面的通用启动能力。

测试报告先写入，再做辅助清理。关闭所属游戏和主机后恢复玩家名。DLL 占用导致清理失败时，保留证据，并将测试驱动移出自动加载目录；不能为了清理而关闭其他游戏、编辑器或操作不属于本轮的防火墙提示。

## 8. 当前证据边界

| 项目 | 已获得的证据 | 限制 |
| --- | --- | --- |
| GUI 与注入 | 定义解析、注入、Wave/JASSHelper/PJASS 检查 | 编译通过不等于实机行为通过 |
| MIX 管理 | 导入导出字节一致、更新保留素材、重复名与截断拒绝 | 不自动转码 |
| 缓存冷启动 | 删除工作目录后，实际游戏从完整 MIX 重建并播放 | 本机环境 |
| 游戏关闭后停止音频 | 真实 WPF 媒体 + 短寿命进程/窗口夹具，父进程仍存活 | 不等于所有平台验证 |
| 双客户端指定停止 | 两个实际 War3 客户端、同一 LAN 局、解码与音频 | 同机、双方安装插件、窗口化 |
| 最新编辑器隔离 | 相同实际 MIX 在 editor/game 名称夹具中分别跳过或启用，真实 WPF 解码 | 未代为保存用户地图；修复后未重跑双客户端 LAN |

双客户端成功轮次在最后清理测试驱动时发生文件占用错误，报告随后由保存的客户端日志、音频记录、host 日志和启动元数据重建。这是报告恢复，不应描述成完整测试驱动无异常运行。

独占全屏、KK 对战平台、新版/Reforged、跨机器和安装/未安装插件混装均未验证。EXE 名称过滤只支持当前已列出的客户端名，换启动器或改名后应重新核对。

## 9. 可复用结论

1. 把视频表现与同步玩法分开，是可选插件兼容设计的基础。
2. 一个 MIX 能降低玩家分发步骤，但仍需设计缓存、升级与并发提取。
3. 多客户端隔离应覆盖整个链路：请求、实例锁、日志、媒体与目标窗口。
4. 插件宿主边界必须尽早检查；被加载不代表应该执行。
5. GUI 精简并不等于隐藏必要语义：指定玩家停止与停止全部需要明确区分。
6. 用实机 LAN 验证多人行为，用夹具验证进程退出与宿主过滤，并明确两者能证明什么。

本文只发布经验与工程边界，不包含游戏、用户地图、用户视频、私人路径或凭据。

## 2026-10-09：v1.0.0 源码与发行包

[源码及下载](https://github.com/Bzsga/war3-video-mix)已补充。管理器支持为 KKWE/YDWE 安装及卸载触发器动作，界面明确作者制作 MIX 与玩家仅放置包的区别。

用户双开日志定位到另一个窗口以 local-skip 停止，而指定窗口是 map-stop：播放器全局 ESC 监听与地图键盘事件冲突。最新版本取消隐式 ESC 跳过，停止由地图动作控制。两个原生窗口夹具加载实际 MIX 后，指定停止一端而另一端音频继续；本次未重新开启真实 LAN 局。版本元数据与 UI 变更通过编译及正常/最小窗口检查。

## 2026-10-09：v1.1.2 快速创建与可选注册表

最新管理器整合作者流程：选择编辑器及魔兽目录、导入视频、自定义名称、一键生成 MIX 到根目录并默认安装触发器动作。程序标记缺失时可确认继续；未知配置布局安装失败时保留生成的包并允许单独重试。原包可合并或替换，保留备份并停用，避免两个视频包并存。用户流程和故障保护已通过目录夹具与实际 WinForms 完成弹窗检查。
